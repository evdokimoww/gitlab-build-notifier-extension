# GitLab build stage notifier

Расширение для **Chromium** (Chrome, Edge, Brave и др.): следит за **открытыми вкладками** с merge request или pipeline на вашем **GitLab**, периодически опрашивает **REST API** и **один раз** сообщает, когда все джобы выбранного **stage** (по умолчанию `build`) завершились успехом или ошибкой.

## Возможности

- Проверка Jira-ссылок в заголовках MR, описаниях и комментариях. Задачи всегда открываются в новых вкладках, сохраняя страницу GitLab. Если ключ существует в обеих Jira, один клик открывает обе страницы.
- Статус авторизации в попапе и настройках: действительность токена GitLab и доступность сессии каждой Jira проверяются запросами к API.
- **Имя готовой сборки на странице MR** — внутри карточки pipeline под статусом появляются полный тег образа и кнопка копирования. Нажатие на тег открывает job. Строка обновляется при опросе, в том числе для уже собранных MR, по которым уведомление отправлялось раньше. При новом pipeline или перезапуске stage старое имя скрывается до успешного завершения stage.
- **Promote MR** — отдельная страница (`promote.html`): цепочка feature → staging → production (маски веток настраиваются), несколько параллельных сессий (вкладки), лог и build-образ по каждой. Фон service worker — вкладку можно обновить. Токен с scope **`api`**.
- Системное **уведомление** браузера с иконкой (успех / ошибка).
- Опциональный **звуковой сигнал** (через offscreen-документ): **разные файлы** для успеха (`sounds/notify.wav`) и ошибки (`sounds/notify-fail.wav`) — при желании замените их своими WAV с теми же именами.
- Префикс **`[CI OK]`** / **`[CI FAIL]`** в заголовке вкладки.
- **Мигание favicon** (`notify-ok.png` / `notify-fail.png`), затем стабильная статусная иконка.
- **Whitelist** путей проектов в GitLab (если нужно ограничить проекты).

Данные учётной записи GitLab **не покидают** ваш браузер: токен хранится в `chrome.storage.local`, запросы идут напрямую с вашей машины к API GitLab.

## Требования

- Браузер на базе Chromium с поддержкой **Manifest V3**.
- Для API: **Personal Access Token** в GitLab с правом **`read_api`** (или шире, если принято у вас в организации).
- Доступ к вашему GitLab по HTTPS (при первом сохранении «чужого» базового URL браузер может запросить **доступ к сайту** — его нужно выдать).

## Установка из исходников

1. Клонируйте репозиторий (или скачайте архив и распакуйте).
2. Откройте `chrome://extensions` (в Edge: `edge://extensions`).
3. Включите **Режим разработчика**.
4. Нажмите **Загрузить распакованное расширение** и укажите папку с `manifest.json`.

После обновления кода нажмите **Обновить** на карточке расширения.

Если расширение уже загружено из папки, замените файлы именно в этой папке и обновите его карточку в `chrome://extensions`. Так сохранятся настройки и токен GitLab. Загрузка из другой папки может создать отдельную копию расширения. В попапе должен отображаться номер `v1.6.4`. Доступ к стандартным адресам GitLab и обеих Jira объявлен при загрузке расширения, отдельное сохранение настроек для него больше не требуется. Если Chrome запросит подтверждение новых разрешений при обновлении, подтвердите его. Затем перезагрузите страницу GitLab. Токен GitLab для проверки Jira не нужен.

## Настройка

1. ПКМ по иконке расширения → **Параметры** (или ссылка «Настройки» в попапе).
2. **Базовый URL GitLab** — например `https://git.example.com` (без лишнего слэша в конце).
3. **Personal Access Token** — создайте в GitLab: *Preferences → Access Tokens* (или *Edit profile → Access Tokens*), вставьте токен в поле.
4. При необходимости измените:
   - **имя stage** (по умолчанию `build`);
   - **интервал опроса** (секунды, ограничен диапазоном в интерфейсе);
   - трактовку **skipped** / **canceled**;
   - включение **мигания favicon** и **звука**;
   - **маски веток** для Promote (staging → production), если флоу отличается от `develop` → `master`/`main`.

Кнопка **«Сбросить уже уведомлено»** очищает кэш: следующее завершение того же пайплайна снова вызовет уведомление (удобно для отладки).

### Ссылки на задачи Jira

Стандартные адреса `https://git-02.t1-group.ru`, `https://tasks.t1-group.ru` и `https://jira.t1-group.ru` включены в разрешения манифеста. Можно изменить оба базовых URL Jira или выключить проверку ссылок. Для нестандартных адресов нажмите «Подключить сайты» в попапе или сохраните настройки и подтвердите запрос браузера. В версиях 1.6.0 и 1.6.1 стандартные адреса также требовали отдельного запроса. Отказ в доступе оставляет ссылки GitLab без изменений, пока доступ не будет выдан.

Расширение обрабатывает ссылки `/browse/KEY-123` на настроенные Jira, в том числе автоматически сформированные GitLab. На страницах настроенного GitLab проверка начинается после загрузки страницы, а новые ссылки в комментариях подхватываются при появлении. Для каждой задачи параллельно выполняются два небольших GET-запроса `/rest/api/2/issue/KEY-123?fields=summary`. Запрашивается только заголовок задачи, без описания, комментариев и вложений. Подтверждение требует JSON с `id` и совпадающим ключом задачи. Страница входа с HTTP 200 не считается найденной задачей.

Для Jira используются cookies текущего профиля браузера через `credentials: include`. Пароль и отдельный токен Jira не нужны, токен GitLab в Jira не отправляется. Запросы выполняются из расширения с разрешением доступа к хостам. Поддержку сессионных cookies описывает [документация Chrome](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies). Если браузер блокирует cookies или корпоративный SSO не принимает сессию в таких запросах, расширение покажет недоступную сессию. Откройте Jira по ссылке входа, войдите обычным способом и повторите проверку. Если обычный вход не помогает, проверьте ограничения cookies и SSO с администратором.

Когда задача найдена только в одной Jira, меняется обычный `href`, а ссылка открывается в новой вкладке. Сохраняются Ctrl/Cmd+клик, средняя кнопка мыши, параметры и фрагмент комментария. Если задача найдена в обеих Jira, один клик создаёт две новые вкладки через API расширения. Первая активируется; при Ctrl/Cmd+клике или средней кнопке обе остаются в фоне. Текущая вкладка GitLab сохраняется. Если проверки ещё выполняются, нажатие показывает прогресс и открывает одну или две вкладки после подтверждения. Контекстное меню для задачи из двух Jira позволяет открыть каждый адрес отдельно. Если ни один адрес не подтверждён, показываются вход или повторная попытка. Ошибка сети, отсутствие авторизации и отсутствие задачи различаются; HTTP 404 также может означать отсутствие прав на просмотр.

Повторные ссылки на один ключ используют общую проверку. Результат хранится в памяти до пяти минут, ошибки авторизации и сети до 15 секунд. Кнопка «Проверить снова» в окне проверки обновляет результат сразу. После загрузки вкладки Jira кеш сбрасывается и ссылки в открытых вкладках GitLab проверяются заново. Проверка работает без токена GitLab и независимо от опроса сборок.

### Статус авторизации

Поле «Personal Access Token GitLab» относится только к GitLab. Попап и настройки проверяют сохранённый токен через `/api/v4/user` без сессии браузера, поэтому вход на сайт GitLab не маскирует истёкший токен. Подтверждённый статус показывает имя пользователя. Для каждой Jira отдельно проверяется `/rest/api/2/myself` с сессией браузера. Разрешение доступа к сайту, необходимость входа, запрет доступа и недоступность сервера показываются отдельно. «Проверить доступ» повторяет проверки сохранённых настроек после входа или замены токена. Успешная проверка пользователя GitLab не подтверждает scope `api` для Promote или доступ к каждому проекту.

### Имя сборки на MR

Мгновенная проверка при открытии MR относится только к строке образа. Она не отправляет уведомления, не меняет их кэш и не влияет на таймер Promote. Общий опрос уведомлений сохраняет исходное расписание; чтение артефактов и логов выполняется отдельно от него.

Блок появляется после успешного завершения выбранного stage, по умолчанию `build`. Для каждого успешного job расширение ищет имя в артефактах `images.txt` и `build.env`, затем в строке `Untagged:` лога. Это тот же способ, который использует Promote. Если образов несколько, у каждого будет своя строка с кнопкой копирования. Пропущенные jobs не читаются; если имя найти не удалось, блок не показывается, а чтение повторяется при следующем опросе. Уведомления продолжают работать независимо от доступности имени.

Имена последних 100 прочитанных jobs сохраняются в памяти сессии браузера. Логи и артефакты для них повторно не скачиваются. После обновления расширения перезагрузите открытую страницу MR: проверка этой вкладки запускается сразу после загрузки, без ожидания фонового таймера. Если сборка ещё выполняется, её завершение отслеживается с настроенным интервалом опроса.

## Как это работает

1. Service worker по таймеру смотрит **все открытые вкладки** и отбирает URL вида:
   - `…/-/merge_requests/<iid>…`
   - `…/-/pipelines/<id>…` (в том числе с хвостом пути: graph, failures и т.п.)
   - `…/-/jobs/<id>…` (страница лога джоба — пайплайн берётся из API по этому джобу)
2. Базовый URL вкладки должен совпадать с настроенным инстансом GitLab.
3. Для MR определяется пайплайн (`head_pipeline` или последний пайплайн MR).
4. Запрашиваются джобы пайплайна; фильтруются по имени **stage** (сравнение **без учёта регистра**, `build` и `Build` совпадают).
5. Если в stage есть джоб в статусе **`failed`**, событие считается **ошибкой сразу** (fail-fast): не ждём остальные джобы вроде `manual` / `pending`, чтобы всё равно прийти к уведомлению, красному favicon и звуку ошибки. Иначе пока есть джобы в «живых» статусах (`running`, `pending`, `canceling`, …) — уведомление не шлётся.
6. Когда исход stage определён (успех или ошибка; с учётом флагов для **skipped** / **canceled** и нормализации статусов в API), один раз отправляются **уведомление**, опционально **звук** (успех или ошибка), обновляются **заголовок вкладки** и **favicon**; пара `(проект, pipeline, stage)` сохраняется, чтобы не дублировать событие.

## Разрешения расширения

| Разрешение        | Зачем |
|-------------------|--------|
| `tabs`            | Найти открытые вкладки MR/pipeline и при необходимости выполнить скрипт на странице (favicon, запасной звук). |
| `storage`         | Настройки и кэш «уже уведомлено». |
| `notifications`   | Системные уведомления. |
| `alarms`          | Периодический опрос без постоянного таймера вручную. |
| `scripting`       | Вставка скрипта на вкладку GitLab (favicon, заголовок, запасной звук). |
| `offscreen`       | Фоновая страница для воспроизведения звука (service worker не может надёжно вызывать `Audio`). |
| host permissions  | Запросы к API GitLab (`/api/v4/…`), работа на его страницах и запросы к двум настроенным Jira. |

## Устранение неполадок

- **Нет всплывающего уведомления**  
  В настройках ОС разрешите уведомления для браузера. На macOS: *Системные настройки → Уведомления → [Chrome/Edge]*. Убедитесь, что для расширения не заблокированы уведомления.

- **Нет звука**  
  Проверьте, что в настройках расширения включён звук. Убедитесь, что после добавления разрешения `offscreen` расширение **перезагружено**. При блокировке автовоспроизведения может сработать запасной вариант через вкладку GitLab.

- **Событие не отслеживается**  
  Проверьте токен, базовый URL, whitelist проекта и что вкладка действительно на нужном хосте и в нужном пути MR/pipeline.

## Проверки

Без установки зависимостей, Node.js 22 или новее:

```sh
node --experimental-default-type=module --test tests/*.test.mjs
```

Для проверок DOM запустите локальный HTTP-сервер из корня репозитория и откройте `tests/mr-build-image.browser.html` в Chromium. Результат `PASS (10)` подтверждает восстановление строки после перерисовки, соответствие pipeline, копирование, отсутствие дублей и очистку при навигации. Страница использует тестовые данные, токен GitLab не требуется.

`tests/jira-links.browser.html` проверяет ссылки в заголовке и описании MR, новые комментарии, открытие в новых вкладках, запрос открытия обеих Jira, Ctrl/Cmd+клик и среднюю кнопку, ожидание проверки перед открытием, параметры и фрагменты, вход, повторную проверку и выключение во время запроса. При переходе в другую Jira параметр автоматического входа `atlogin` удаляется; на исходной Jira сохраняется. Сетевые ответы подменяются тестовыми данными.

`tests/jira-onboarding.browser.html` воспроизводит чистую установку через настоящий попап и фоновую логику: отсутствие разрешений, отказ, повторное подключение и исправление ссылки в уже открытой странице без токена GitLab. Подменяются только API браузера и серверные ответы.

`tests/auth-status.browser.html` проверяет, что запоздавший ответ предыдущей проверки не возвращает старого пользователя и не включает кнопки во время новой проверки.
